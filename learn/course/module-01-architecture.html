🏗️ Architecture & the request lifecycle

The whole system on one page: what each piece does, the two request paths, and the reasoning that makes this "a portfolio project" instead of "a tutorial".

1 · The 90-second pitch (learn to say this cold)

In an interview, the first question is almost always "tell me about your project". You want a version you can deliver in ~90 seconds, then let them dig. Say it out loud until it's smooth:

🎤 Say this

"It's a multi-user expense tracker that runs entirely serverless on AWS. The frontend is a static single-page app on S3, served over HTTPS through CloudFront on a custom domain. Users authenticate with Cognito, which issues a JWT. Every API call carries that JWT to API Gateway, which verifies the signature at the edge — so Lambda never sees an untrusted identity. It routes to a single router Lambda that does the business logic against DynamoDB, where the partition key is the Cognito sub — so a user can only ever read their own rows; that's the tenant isolation. Receipts upload straight from the browser to a private S3 bucket via presigned URLs. In V3, an S3 event triggers a second Lambda that reads the receipt with Bedrock's Nova Lite vision model and fills the expense in asynchronously — the row appears instantly and the AI call can fail without blocking the user. The whole stack is CloudFormation, tested offline with pytest+moto, green in CI, runs in the EU, and costs effectively nothing at rest."

💡 Interview craft

Notice what that does: it names every service, gives a reason for the interesting ones (edge verification, tenant isolation, async OCR, cost), and ends on a principle. That invites the follow-up you want ("tell me about the tenant isolation").

4 · Two lifecycles — and why they are different

This is the single most important idea in the project. Step through both.

Path A — synchronous CRUD ("add an expense")

The user waits, so it must be fast and predictable.

Path B — asynchronous OCR ("scan a receipt")

An AI vision call is slow and can fail. Watch exactly where the user's request ends — that's the whole design.

🔑 The insight to remember

In Path B, the user's request finishes after the S3 upload, before the AI ever runs. The AI work is decoupled behind an S3 event, so it can take seconds, retry, or fail — and the user's experience never breaks. That's the difference between a demo and an architecture.

5 · Why these choices — the trade-off table you must own

Every design question is really "why this and not that". Open each one:

Serverless (Lambda + managed services) — why not EC2 / containers?

We chose it because: no idle cost (pay per request), no servers to patch, scales to zero and to spikes automatically, and managed HA comes for free. The alternative — EC2/ECS — means paying 24/7 for an idle box, patching an OS, and building your own scaling and health checks.

DynamoDB — why not RDS / Aurora?

We chose it because: on-demand pricing (no idle cost), single-digit-ms lookups at any scale, and the partition key doubles as the tenant boundary. RDS/Aurora would bill hourly even when idle and add connection-management complexity. The price we pay: no joins, no SQL, and our /summary does a read-then-aggregate instead of a GROUP BY.

HTTP API — why not REST API?

We chose it because: ~70% cheaper and it has a native JWT authorizer — exactly what we need. REST API has more features (API keys, request validators, WAF integration, usage plans) that we simply don't use, at a higher price.

CloudFront — why not serve S3 directly?

We chose it because: the S3 website endpoint is HTTP only (browsers warn "Not secure"), so CloudFront gives us real HTTPS/TLS, a custom domain with an ACM cert, edge caching, compression, HTTP/2, and it hides the bucket. Serving the raw S3 website is insecure and unbranded.

Bedrock (Nova Lite) — why not Textract or Rekognition?

We chose Bedrock because: one call returns structured JSON and it has an EU inference profile (respecting our data-residency principle). Textract AnalyzeExpense is the purpose-built service but is gated on this account; Rekognition DetectText works but returns raw text only — we'd own all the parsing.

Route 53 + ACM — why not just the *.cloudfront.net URL?

We added it because: a real product needs a real name and a padlock on your domain. The default CloudFront domain works, but it isn't a product name — and it can't do apex/root records, which a portfolio piece should show you understand.

6 · The four principles that tie it together

  1. EU data residency — everything in eu-central-1; the Bedrock eu. inference profile keeps the image in the EU. (Decision D1.)
  2. Least privilege — each Lambda runs as a role that can touch only what it needs.
  3. Tenant isolation — identity comes from the verified JWT sub, never the request body; it's the partition key.
  4. No idle cost — nothing runs (or bills) when nobody is using it.

8 · 🧠 Quiz — 15 deep questions

Answer from memory first, then reveal and grade yourself honestly. Your score saves automatically.

Graded 0 / 15 · Score 0 / 15

  1. Give the 90-second pitch of the project from memory — no notes. (Record yourself; does it name every service and give a reason?)

    Use the script in §1. The beats: serverless expense tracker → static SPA on S3 behind CloudFront (HTTPS, custom domain) → Cognito issues JWTs → API Gateway verifies the token at the edge → one router Lambda → DynamoDB keyed by the Cognito sub (tenant isolation) → receipts go browser→S3 via presigned URLs → an S3 event triggers an OCR Lambda that uses Bedrock vision, asynchronously → CloudFormation + tests + CI → EU, ~free at rest.

  2. Trace the exact path of the bytes for "add an expense" — name every service the request touches, in order.

    Browser (holds the JWT from an earlier Cognito sign-in) → API Gateway (verifies the JWT signature + iss/aud/exp using Cognito's cached JWKS) → Lambda (router matches POST /expenses, sets userId = claims.sub, validates) → DynamoDB (PutItem) → response back up the chain as {statusCode, headers, body} → browser re-renders. Note the static assets themselves came from CloudFront → S3, not from the API.

  3. Now trace the OCR path. At which exact point does the user's request finish, and why does that matter?

    POST /expenses/scan creates a pending row and returns a presigned PUT URL; the browser then PUTs the image straight to S3. The user's request finishes when that upload succeeds — before the AI runs. S3's ObjectCreated event then invokes the OCR Lambda asynchronously; Bedrock reads the image and the Lambda UpdateItems the row to processed/needs_review; the browser polls GET /expenses to see it. Why it matters: a slow, fallible AI call is decoupled from the user's experience — the UI is instant and the AI step can retry or fail without blocking anyone.

  4. Name all the AWS services used, and give each a one-line job.

    CloudFront HTTPS/caching front door · S3 static hosting + private receipts · Cognito accounts/JWTs · API Gateway (HTTP API) routes + JWT authorizer · Lambda business logic (api + ocr + autoconfirm) · DynamoDB expense records · IAM least-privilege roles · Bedrock receipt vision · Route 53 DNS · ACM TLS certificate · CloudWatch logs. (Also CloudFormation as IaC, though that's tooling rather than a runtime service.)

  5. Why serverless over EC2/containers? Give three distinct reasons (not three versions of the same one).

    Any three of: (1) cost model — pay per request, zero idle cost; (2) no ops — no OS patching, no capacity planning, no servers to secure; (3) elasticity — scales from zero to spikes automatically, including down to zero; (4) managed HA/fault tolerance across AZs for free; (5) faster delivery — you assemble managed services instead of building infrastructure; (6) security surface — each function gets its own minimal IAM role.

  6. Why DynamoDB and not RDS/Aurora? What capability do you give up?

    Why: on-demand (no idle cost), single-digit-ms at any scale, no connection pooling to manage, and the partition key itself enforces tenant isolation. What we give up: joins and multi-table transactions, ad-hoc SQL/analytics, and flexible secondary indexing. Concretely, our /summary reads all of a user's items and aggregates in Lambda — fine for one user, but a relational GROUP BY would be simpler and cheaper at large scale.

  7. Why is CloudFront in front of the web bucket? Give two different reasons.

    (1) Security / trust: the S3 website endpoint is HTTP-only — browsers flag it "Not secure". CloudFront terminates TLS, so we get HTTPS + a padlock + a real custom domain (ACM cert). (2) Performance/cost: it caches the static assets at edge locations nearest the user, compresses them, speaks HTTP/2, and absorbs load/DDoS — so S3 sees far fewer requests. Extras: it hides the origin bucket, and gives custom error pages.

  8. Our CloudFront origin is the S3 website endpoint over HTTP, not an Origin Access Control (OAC) bucket. What's the trade-off, and what would you change for production?

    Trade-off: the website endpoint requires the bucket to be publicly readable, so anyone who learns the bucket URL can bypass CloudFront entirely (skip caching, bypass any CloudFront-layer rules, and see the bucket directly). The CloudFront→origin hop is plain HTTP (though it stays inside AWS). Production fix: switch the origin to the S3 REST endpoint with an OAC, keep the bucket fully private, and add a bucket policy that allows only this distribution. Bonus: add a CloudFront Function for SPA routing and a WAF.

  9. Where does the user's identity come from, and why is that the security backbone of the app? What breaks if you trusted a userId from the request body?

    Identity comes from event.requestContext.authorizer.jwt.claims.sub — the verified sub of the Cognito JWT, injected by API Gateway's authorizer after it checks the signature. Why it's the backbone: userId is the DynamoDB partition key, so Query(userId == sub) can only ever return the caller's rows. If we trusted the body: any signed-in user could send someone else's userId and read/modify/delete their expenses — a classic IDOR / broken object-level authorization bug. Because we never read identity from user input, that class of bug is impossible by construction.

  10. Why is the system "no idle cost"? Name a service choice that would have introduced idle cost, and why we avoided it.

    Every runtime service is pay-per-use or storage-only: Lambda (per request/GB-s), API Gateway (per request), DynamoDB on-demand (per read/write), S3 (per GB + request), Cognito (per MAU), CloudFront (per request/GB). Nothing runs when idle. Idle-cost traps we avoided: RDS/Aurora (bills hourly even with zero traffic), EC2/ECS/ALB (always-on), a NAT Gateway (~$32+/mo just to exist), or ElastiCache. The one standing cost is the Route 53 hosted zone ($0.50/mo), which is a fixed DNS fee, not compute.

  11. The app runs in eu-central-1, but the ACM certificate had to be in us-east-1. Explain why, and how that didn't violate your EU-residency principle.

    Why us-east-1: CloudFront is a global service and AWS only accepts ACM certificates from us-east-1 (N. Virginia) for it — a hard platform requirement (regional services like ALB use a cert in their own region instead). Why residency is intact: a TLS certificate is public material — public key and domain names — it contains and processes no user data. All user data, compute and the Bedrock inference stay in eu-central-1. So the EU-residency principle (which is about data) is unbroken.

  12. We have two data stores (DynamoDB and S3). Why two, and what rule decides which piece of data goes where?

    DynamoDB holds the structured, queryable, tenant-scoped records we need to filter/sort/aggregate (expenses). S3 holds the large binary objects (receipt images up to 5 MB) that don't belong inside a database row and are better served by presigned URLs. The rule: small structured data you query → DynamoDB; large unstructured blobs you store/serve → S3. And we keep only a reference (receiptKey) in DynamoDB — the pointer, not the bytes.

  13. What is the single most important design decision in this architecture, and why?

    There's no single "correct" answer — an interviewer wants a defensible pick with reasoning. Strong answer: deriving identity from the verified JWT and making it the partition key, because it collapses security (no IDOR possible) and data access (fast, single-partition Query) into one decision. Equally defensible: going fully serverless (the cost/ops model), or decoupling the AI step behind an S3 event (resilience). Name your pick, then justify the trade-off you accepted.

  14. If traffic grew 1000×, what breaks first, and why? (Hint: a single Lambda's limits, and a single partition key.)

    Lambda account concurrency first — the default is 1000 concurrent executions per region, and we literally hit throttling (our load test produced 503s). Next, for OCR, Bedrock on-demand throughput quotas (tokens/requests per minute) would throttle the async pipeline. Also risk: a single user's hot partition (DynamoDB per-partition limits) if one account writes very fast. Fixes: request a concurrency increase, add reserved/provisioned concurrency, use SQS between S3 and the OCR Lambda to smooth and retry, and consider write sharding for hot tenants.

  15. What is your "phase 2", and why did you deliberately defer it?

    Phase 2 (from the README): budgets/targets, Cognito groups for RBAC, monitoring alarms + X-Ray, rate limiting / WAF, a real deploy job in CI, and push/WebSocket instead of polling. Why defer: each is an independent enhancement that adds surface area without changing the core story — and an unfinished pile of half-features is worse than a small, complete, well-understood system. Deferring them (and knowing why) demonstrates scope discipline, which is itself an engineering signal.
